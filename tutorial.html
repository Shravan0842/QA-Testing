1 Introduction to Software Testing

What is Software Testing?

Software testing is the process of evaluating a software application to verify it works as expected and meets specified requirements. It is the systematic activity of identifying defects, errors, and missing functionality before the product reaches the user.

According to T Point Tech, testing is defined as: "a group of techniques to determine the correctness of the application under the predefined script." Guru99 emphasizes that testing is the process of executing a program with the intent of finding bugs. GeeksforGeeks adds that it improves software quality by detecting and fixing defects early.

Definition Comparison (across the 3 sources)

Source Definition of Software Testing Key Emphasis
Guru99 "Testing helps to identify errors, gaps or missing requirements." Defect discovery
GeeksforGeeks "The process of evaluating a software application to verify that it works as expected and meets specified requirements." Verification & validation
T Point Tech "A process of identifying the correctness of software by considering its all attributes (Reliability, Scalability, Portability, Re-usability, Usability)." Quality attributes

2 Why Software Testing Matters

Software failures are not just bugs — they're business disasters. GeeksforGeeks lists several real-world incidents that prove the cost of untested software.

Year Incident Cause / Impact What Testing Could Have Caught
1985 Therac-25 radiation machine malfunction Deaths and injuries Race-condition and interlock testing
1994 China Airlines Flight 140 crash Software bug killed 264 people Edge-case input validation
1996 U.S. bank error $920M wrongly credited to 823 customers Transaction boundary tests
1999 Military satellite launch failure $1.2B lost Integration & stress testing
2015 F-35 fighter jet bug Defective target detection Sensor fusion testing
2015 Bloomberg terminal crash Disrupted 300,000 traders globally Load & failover testing
— Starbucks POS failure Shut 60% of U.S./Canada stores Hardware-software integration tests
— Nissan recall 1M cars due to airbag software Embedded systems & safety tests

Key Reasons to Test

  • Defect detection — find bugs before users do.
  • Quality assurance — ensures a reliable, secure, high-performing product.
  • Risk reduction — catches issues early when fixing is cheap.
  • UX protection — UI/UX testing keeps customers happy.
  • Cost savings — a bug caught in design costs 10× less than one caught in production.
⚠️ Industry rule of thumb: The cost to fix a bug grows exponentially across the SDLC. A requirements bug fixed at design time might cost ₹1,000; the same bug caught in production could cost ₹1,00,000+ in support, patches, and reputation damage.

3 The 7 Principles of Testing

Guru99 lists seven core principles. They are universal — they apply to every project, every methodology, every team. Memorize them; you'll be asked in interviews.

# Principle Meaning Real-World Example
1 Testing shows the presence of defects, not their absence Testing reduces the probability of undiscovered bugs but cannot prove there are none. Even after 1,000 tests pass, the next user action may break the app.
2 Exhaustive testing is impossible You can't test every input. Use risk and priorities instead. A 10-digit phone field has 10 billion combinations — you test only valid, invalid, and edge cases.
3 Early testing saves time & money Find defects as early as possible. A bug found in requirements is fixed by editing a doc; the same bug in production requires a hot-fix release.
4 Defects cluster together A small number of modules usually contain most of the bugs (Pareto 80/20). The "Checkout" module of an e-commerce site breaks more often than "About Us".
5 Be wary of the pesticide paradox Repeating the same tests stops finding new bugs. Update tests regularly. If you run the same regression suite for 6 months without updating it, you will miss new defects.
6 Testing is context-dependent Different software requires different testing approaches. A banking app needs heavy security testing; a game needs performance testing.
7 Absence-of-errors is a fallacy A bug-free system can still be unusable if it doesn't meet user needs. A bug-free calculator app no one wants is still a failure.
💡 Interview tip: When asked "What are the principles of testing?" answer with the table above and a one-line example for each. Interviewers love concrete examples over textbook definitions.

4 SDLC & Development Models

SDLC (Software Development Life Cycle) defines how software is built. The choice of model shapes when and how testers work.

Model Flow When Testing Happens Best For Drawback
Waterfall Req → Design → Code → Test → Deploy (linear) Only after build, in the "Test" phase Small, well-defined projects with stable requirements Late feedback; expensive changes
V-Model Each dev phase has a matching test phase Planned in parallel with development Safety-critical systems (medical, aviation) Still rigid, like Waterfall
Agile (Scrum) 2–4 week sprints with continuous test & release Throughout every sprint, end-to-end Most modern products, fast-changing requirements Requires experienced, self-organized teams
Spiral Cycles of plan → risk → build → evaluate Each spiral iteration Large, complex, high-risk projects Expensive; needs strong risk expertise
Prototype Build a quick prototype → gather feedback → rebuild Each prototype iteration Unclear requirements; need user validation May cause scope creep

5 STLC — Software Testing Life Cycle

STLC defines what testing activities happen from the moment a requirement arrives until the product is released. T Point Tech and Guru99 both cover the 6 phases.

Phase What You Do Output / Deliverable Entry Criteria Exit Criteria
1. Requirement Analysis Review requirements; identify testable items; ask clarifying questions. RTM (Requirements Traceability Matrix), testable requirements list. Requirements docs available. All requirements reviewed and ambiguities cleared.
2. Test Planning Define strategy, scope, resources, schedule, tools, risks. Test Plan document. Requirements analysis done; team & budget approved. Test Plan reviewed and signed off.
3. Test Case Development Write detailed test cases, test scripts, and test data. Test cases, test data, RTM. Test plan approved. Test cases reviewed and signed off.
4. Test Environment Setup Build/hardware/software setup for executing tests. Ready test environment with test data loaded. Test cases ready; environment spec defined. Smoke test passed on environment.
5. Test Execution Run test cases; log results; report bugs. Test execution report, bug reports. Environment ready; test cases & data ready. All planned test cases executed; critical bugs resolved.
6. Test Closure Summarize results; analyze metrics; lessons learned; archive artifacts. Test Closure Report. All tests executed or deferred; defect triage done. Closure report signed off; deliverables archived.

💡 Pro tip: Each STLC phase has Entry and Exit Criteria. Exit criteria are your "definition of done" for that phase. If you can't meet them, the next phase shouldn't start. This prevents late-stage surprises.

6 Levels of Testing

Test levels describe how much of the system is being tested at a time — from a tiny function up to the full business workflow.

Level What's Tested Who Tests Example Bug Type Caught
1. Unit Testing Individual functions/methods in isolation. Developers Testing the calculateTax() function with various inputs. Logic errors, arithmetic mistakes.
2. Integration Testing How modules talk to each other. Developers / SDETs Does the Login module correctly pass user data to the Profile module? Interface mismatches, data format issues.
3. System Testing The complete integrated system. QA team Testing the full e-commerce checkout flow end-to-end. Missing features, broken workflows.
4. User Acceptance Testing (UAT) Business scenarios from real users' perspective. Client / Product owner / end users "As a customer, can I return an item and get a refund within 7 days?" Misalignment with real business needs.

The "Testing Pyramid"

             /\
            /  \          UI / E2E Tests (slow, few)
           /────\         ─────────────────────
          /      \        Integration Tests (moderate)
         /────────\       ─────────────────────
        /          \      Unit Tests (fast, many)
       /____________\

      ▲ Cheap & Fast to fix bugs at the bottom
      ▲ Hard & Costly to fix bugs at the top
💡 Why this matters: Aim for many unit tests, some integration tests, and few E2E tests. UI tests are slow and brittle — they catch the least bugs for the most effort.

7 Types of Software Testing

All three sources categorize testing into Functional vs Non-Functional. Within each, there are dozens of sub-types.

Functional Testing — "Does it do what it should?"

Type What it Tests Real Example
Unit Testing Smallest testable unit of code. Testing if a function correctly calculates discount.
Integration Testing Interaction between modules. Does "Add to Cart" correctly update the inventory API?
System Testing Complete integrated product. Full order placement flow including payment, email, and shipping.
Smoke Testing Build's critical paths work; build is stable enough for deeper testing. After a new build, check: app opens, login works, dashboard loads.
Sanity Testing Specific bug fix or new feature works; narrow & deep. After fixing the "password reset" bug, verify reset works end-to-end.
Regression Testing Old features still work after a change. After adding a new payment method, ensure card and UPI still work.
User Acceptance Testing (UAT) Real user validates the product. Client tests the app with real data and real workflows before launch.
Alpha Testing Internal testing at the developer's site. QA team tests pre-release build in a controlled environment.
Beta Testing External testing by a limited audience. 1,000 users get a beta build of the new Instagram Reels editor.

Non-Functional Testing — "Does it perform, scale, and stay safe?"

Type What it Tests Real Example
Performance Testing Speed, response time, stability under load. How fast does the homepage load with 10,000 concurrent users?
Load Testing Behavior under expected load. Simulating 5,000 users browsing during a sale.
Stress Testing Behavior beyond expected load. Pushing 20,000 users to find the breaking point.
Security Testing Vulnerabilities, data leaks, attacks. SQL injection, XSS, broken authentication.
Usability Testing Ease of use, UX, accessibility. Can a first-time user complete checkout in under 2 minutes?
Compatibility Testing Works across browsers, devices, OS versions. Does the app work on Chrome, Safari, Edge, and Firefox?
Reliability Testing App stays functional for a long time. Server runs for 72 hours without crashing.

8 Manual vs. Automation Testing

Guru99 and T Point Tech both emphasize: these are complementary, not rivals.

Aspect Manual Testing Automation Testing
Definition Test cases executed by a human without tools. Test cases executed by scripts and tools.
Speed Slow; human-paced. Fast; runs hundreds of tests in minutes.
Accuracy Prone to human error. Consistent, repeatable.
Best for Exploratory, UX, ad-hoc, one-off testing. Regression, smoke, data-driven, performance.
Cost Low upfront, high long-term (people-hours). High upfront, low long-term (re-runnable).
Skill needed Domain knowledge, attention to detail. Programming + tool expertise (Selenium, Cypress, etc.).
Example Manually testing whether a new feature feels intuitive. A Selenium script auto-tests login for 100 user accounts every night.

When to Use Each

USE MANUAL WHEN:
  ✓ Requirements change frequently (UI prototypes)
  ✓ Test is exploratory (no clear pass/fail)
  ✓ UX / usability is the goal
  ✓ One-off / short-lived tests

USE AUTOMATION WHEN:
  ✓ Test runs repeatedly (regression, smoke)
  ✓ Stable features with clear pass/fail
  ✓ Large data sets (data-driven)
  ✓ Cross-browser / cross-device matrix
💡 Pro tip: A common mistake is trying to automate everything. Start with manual, stabilize the tests, then automate the ones that run repeatedly. The rule: automate what's boring, keep manual what's exploratory.

10 Test Design Techniques

These techniques help you design fewer but smarter test cases that cover more logic with less work. Guru99, GeeksforGeeks, and T Point Tech all emphasize these.

Technique What it Does Best For Real Example
Equivalence Partitioning (EP) Divide inputs into groups that should behave the same. Test one value from each group. Reducing input combinations. For an age field (1–100), test 25 (valid) and 150 (invalid) instead of all 100 values.
Boundary Value Analysis (BVA) Test the edges of valid/invalid partitions (where bugs cluster). Numeric ranges, dates, length fields. For age 1–100, test 0, 1, 100, 101 — the boundaries.
Decision Table Testing Map combinations of conditions to actions. Business rules with multiple inputs. Login: (valid user + valid pwd) → success. (valid user + invalid pwd) → "wrong pwd". (invalid user) → "no account".
State Transition Testing Test how the system changes state based on events. Workflows, lifecycle systems. Order: New → Paid → Shipped → Delivered. Try invalid transitions like New → Delivered.
Use Case Testing Test end-to-end user scenarios. Capturing real user journeys. "As a user, I can search, add to cart, checkout, and receive a confirmation."
Error Guessing Use experience to guess where bugs might hide. No formal design; relies on tester skill. Test with: empty fields, special characters, very long input, copy-paste, double-click.

11 BVA & Equivalence Partitioning — Deep Dive

These two techniques are interview favorites. They are the foundation of black-box test design and a must-know for any QA interview.

Example: A "Discount" Field

A field accepts a discount percentage from 0 to 50.

Step 1: Identify Equivalence Partitions

Partition Range Test Value (one per partition) Expected Result
Invalid (below range) −∞ to −1 −5 Error: "Invalid discount"
Invalid (below valid boundary) −1 to −0.01 −0.5 Error: "Invalid discount"
Valid 0 to 50 25 Accept: 25% off
Invalid (above valid boundary) 50.01 to 100 75 Error: "Invalid discount"
Invalid (above range) 100+ 999 Error: "Invalid discount"

Step 2: Apply Boundary Value Analysis

Test the values at the edges of the valid range: −1, 0, 1, 49, 50, 51.

Input Boundary Type Expected
−1 Just below valid Reject
0 Lower valid boundary Accept (no discount)
1 Just above lower Accept
25 Mid (EP test) Accept
49 Just below upper Accept
50 Upper valid boundary Accept (max discount)
51 Just above valid Reject

Step 3: Compare EP vs. BVA

Aspect Equivalence Partitioning Boundary Value Analysis
Tests what One value from each valid/invalid group. Values at the edges of groups.
Why Values in a group should behave the same. Bugs cluster at boundaries (off-by-one).
When to use When you have many inputs and limited time. When the input is a range, length, or count.
Count for our example 5 test cases (one per partition). 6 test cases (at the boundaries).
💡 Interview tip: When asked "What's the difference between BVA and EP?", answer: "EP divides inputs into groups that should behave the same — test one from each. BVA targets the edges of those groups because that's where bugs hide. They are used together: EP for breadth, BVA for depth."

12 Writing Test Cases

A test case is a set of preconditions, inputs, actions, and expected results used to verify a specific feature. Guru99's "Sample Test Case Template" is the industry standard.

Anatomy of a Test Case

Field Description Example
Test Case ID Unique identifier. TC_LOGIN_001
Test Description What are we testing? Verify login with valid credentials.
Preconditions State needed before the test. User account exists; app is on the login page.
Test Steps Numbered actions. 1. Enter email. 2. Enter password. 3. Click Login.
Test Data Inputs. email: user@test.com, pwd: Pass@123
Expected Result What should happen. User is redirected to the dashboard.
Actual Result What actually happened. User redirected to dashboard with welcome message.
Status Pass / Fail / Blocked / Skipped. Pass
Executed By / Date Who ran it and when. Shravan / 2026-09-03

Real Example: Test Cases for a Login Page

ID Scenario Steps Test Data Expected Type
TC_L_001 Valid login Enter email, pwd, click Login user@test.com / Pass@123 Redirect to dashboard Positive
TC_L_002 Invalid password Enter email, wrong pwd, click Login user@test.com / Wrong "Invalid credentials" error Negative
TC_L_003 Empty email Leave email blank, enter pwd, click Login "" / Pass@123 "Email is required" error Validation
TC_L_004 Empty password Enter email, leave pwd blank, click Login user@test.com / "" "Password is required" error Validation
TC_L_005 SQL injection in email Enter SQL in email field ' OR '1'='1 Login rejected (no DB access) Security
TC_L_006 Case sensitivity Enter email in uppercase USER@TEST.COM / Pass@123 Login successful (case-insensitive) Boundary
TC_L_007 Forgot password link Click "Forgot password?" — Redirect to reset page UI

Test Case vs. Test Scenario

Aspect Test Case Test Scenario
Definition Detailed "how to test" with steps and data. High-level "what to test" — a single line.
Level Low-level, specific. High-level, abstract.
Example Step 1: Enter email, Step 2: Enter pwd, Step 3: Click Login. Expect: dashboard. "Verify login works with valid credentials."
Count Many per scenario (different data, paths). One per feature area.

If a bug fails retest, it goes back to In Progress. If it can't be fixed in this release, it may be Deferred. If it's not actually a bug, it's Rejected. If it's a duplicate of another bug, it's marked Duplicate.

The Bug States Explained

State Meaning Trigger
New Just logged, not yet reviewed. Tester files the bug.
Assigned Sent to a developer. Lead/Manager triages and assigns.
Open / In Progress Developer is working on it. Developer picks it up.
Fixed Developer claims it's fixed. Code change deployed.
Retest / Verify Tester is verifying the fix. Tester re-runs the failing scenario.
Reopened Fix didn't work. Tester sees the same failure.
Closed Verified fixed, done. Tester confirms the fix.
Deferred Won't fix in this release. Out of scope, low priority.
Rejected Not a real bug. By design, can't reproduce, etc.
Duplicate Already reported. Another bug covers this.

Severity vs. Priority

This is a very common interview question. Severity is technical impact; Priority is business urgency.

Combination Severity Priority Example
High / High Critical Fix immediately Login is broken — no one can use the app.
High / Low Critical Fix later Internal-only admin tool crash — only devs see it.
Low / High Minor Fix immediately Logo is upside-down on the homepage — embarrassing brand issue.
Low / Low Minor Fix when possible Typo in a hidden settings page no one visits.
💡 Rule of thumb: Severity is set by the tester based on technical impact. Priority is set by the product manager based on business impact. They don't always match.

14 Agile Testing

Agile testing happens continuously, every sprint. The whole team owns quality, not just the QA team.

The Scrum Framework

Role / Ceremony What It Is QA's Involvement
Product Owner Owns the product backlog. Decides what to build. Clarity on acceptance criteria for user stories.
Scrum Master Facilitates Scrum, removes blockers. Not a manager — but helps the QA team stay unblocked.
Development Team Builds the product (devs, QA, designers). QA is part of the team; everyone shares responsibility.
Sprint Planning Team commits to a sprint backlog. QA estimates testing effort for each story.
Daily Standup 15-min sync: yesterday, today, blockers. QA reports test progress and blockers.
Sprint Review Demo completed work to stakeholders. QA presents what was tested and any quality concerns.
Sprint Retrospective Team reflects: what to start, stop, continue. QA suggests process improvements.
Backlog Refinement Ongoing grooming of upcoming stories. QA asks clarifying questions, identifies testable criteria.

Definition of Done (DoD) vs. Definition of Ready (DoR)

Definition of Ready (DoR) Definition of Done (DoD)
When Before a story enters a sprint. When a story is finished.
Purpose Ensures the team can work on it. Ensures the team has finished it.
Checklist Clear acceptance criteria, estimated, dependencies identified, testable. Code complete, reviewed, unit tested, integrated, regression tested, accepted by PO, documentation updated.

15 Performance Testing

Performance testing measures speed, responsiveness, and stability under various workloads. Guru99 lists 13+ sub-types — here are the most important ones.

Type Goal Real Scenario
Load Testing Test under expected user load. 5,000 concurrent users on Flipkart during a normal day.
Stress Testing Test beyond expected load to find the breaking point. Push 50,000 users to see when the server crashes.
Spike Testing Test sudden, large spikes in load. Flash sale: traffic goes from 1,000 to 100,000 users in 1 minute.
Endurance / Soak Testing Test sustained load over a long time. Run 5,000 users for 24 hours to find memory leaks.
Volume Testing Test with large amounts of data. Database with 10 million records — does search still work?
Scalability Testing Test the ability to scale up/out. Add more servers — does the app use them?
Benchmark Testing Compare against a known standard. Compare new release's response time against the previous one.

Key Performance Metrics

Metric What It Measures Acceptable Range (typical)
Response Time Time from request to first byte. < 200 ms (web), < 1 s (API)
Throughput Requests handled per second. Depends on app
Concurrent Users How many users can be active at once. Per business SLA
Error Rate % of failed requests under load. < 0.1%
CPU / Memory Resource usage under load. < 80% sustained

16 Key Comparisons (Interview Essentials)

These are the most-asked software testing comparison questions. Master the table — it covers ~80% of "compare X vs Y" interview questions.

Verification vs. Validation

Aspect Verification Validation
Question Are we building the product right? Are we building the right product?
Type Static (no code execution). Dynamic (code is executed).
Activities Reviews, walkthroughs, inspections. Functional, system, UAT testing.
Example Reviewing the test plan before testing. Running the login test and verifying the dashboard appears.

QA vs. QC

Aspect QA (Quality Assurance) QC (Quality Control)
Focus Process — preventing defects. Product — finding defects.
Type Proactive. Reactive.
When Throughout the SDLC. During the testing phase.
Example Defining coding standards, review checklists. Running tests and logging bugs.

Smoke vs. Sanity Testing

Aspect Smoke Sanity
Scope Wide — covers critical end-to-end flows. Narrow — covers specific module or bug fix.
When Initial build check ("is it stable enough to test?"). After a fix or small change.
Goal Verify the build is stable. Verify the logic is correct.
Example New build: app opens, login works, dashboard loads. After fixing password reset bug: test only the reset flow.

Retesting vs. Regression Testing

Aspect Retesting Regression
Purpose Re-run a specific test that previously failed. Ensure nothing else broke after a change.
Trigger Bug is fixed. Any code change.
Scope Just the failing test. All impacted and related tests.
Example Login failed → dev fixed → re-test login. After fixing login, also test: dashboard, profile, logout, signup.

SDLC vs. STLC

Aspect SDLC STLC
Scope The entire software development process. Only the testing activities.
Phases Req, Design, Code, Test, Deploy, Maintain. Req Analysis, Plan, Cases, Env, Execute, Closure.
Who Everyone (devs, QA, BA, PM). Mostly the testing team.

Alpha vs. Beta Testing

Aspect Alpha Beta
Where Developer's site (internal). Customer's site (external).
Who Internal testers (QA team). Limited real users.
Environment Controlled, lab-like. Real-world.
Goal Catch major issues before external release. Get user feedback, find edge-case issues.

18 Career Path in Software Testing

Software testing is an evergreen career in IT — there's always demand, and the entry barrier is lower than development.

Typical Career Progression

Level Role Years of Experience Focus Typical Skills
1 QA Analyst / Junior Tester 0–2 Writing & executing test cases. Manual testing, JIRA, test case design, basic SQL.
2 QA Engineer 2–4 End-to-end testing, automation basics. Selenium, Postman, test plans, agile.
3 Senior QA Engineer 4–6 Mentoring, framework design. Advanced automation, CI/CD, performance, security basics.
4 QA Lead / Test Lead 6–8 Managing a team, planning, strategy. Test strategy, metrics, stakeholder mgmt.
5 QA Manager / Test Manager 8+ Department ownership, hiring, roadmap. Process improvement, budgeting, KPIs.
Alt path SDET (Software Development Engineer in Test) 2+ Heavy automation, building tools. Strong coding, framework architecture.

20 Test Estimation Techniques

Test estimation is the process of predicting how much effort, time, and resources are needed to test a project. Accurate estimates help with planning, budgeting, and setting realistic release dates. No method is 100% accurate — the goal is to be consistently close, not perfectly right.

Common Estimation Techniques

Technique How It Works Best Used When Pros / Cons
Expert Judgment One or more experienced testers give an estimate based on similar past projects. When you have historical data and senior people available. + Fast.
− Subjective; depends on who you ask.
Wideband Delphi Team of experts estimate anonymously in rounds; differences are discussed until consensus. Medium-to-large projects with multiple test areas. + Reduces bias.
− Time-consuming; needs facilitation.
3-Point (PERT) Estimate three values: Optimistic, Most likely, Pessimistic. Formula: (O + 4M + P) / 6 When tasks have uncertainty (most real testing work). + Accounts for risk.
− Needs three separate estimates per item.
Work Breakdown Structure (WBS) Break the project into small tasks; estimate each; sum them up; add contingency. Detailed, well-defined projects. + Very thorough.
− Can be over-detailed for agile sprints.
Use-Case Points (UCP) Count use cases, weight by complexity (simple/avg/complex), adjust by technical & environmental factors. Object-oriented / use-case driven projects. + Standardized.
− Complex to compute; less common in agile.
Function Points (FP) Count user functions (inputs, outputs, queries, files, interfaces); convert to effort using a baseline. Large enterprise / data-processing systems. + Industry-recognized.
− Heavy to set up; rarely used in modern agile teams.
Top-Down / Bottom-Up Top-down: estimate the whole, split into parts.
Bottom-up: estimate parts, sum up. 		Top-down for early estimates; bottom-up for sprint planning. + Flexible.
− Top-down can be wildly inaccurate without detail.
Past Data / Analogous Use actual effort from a similar previous project as a baseline, then adjust for size/complexity differences. Organizations with good historical metrics. + Data-driven.
− Only as good as your past data.

PERT (3-Point) — Worked Example

You're estimating the effort to test a checkout module. You have three estimates:

  • Optimistic = 4 person-days (everything goes smoothly)
  • Most likely = 7 person-days (realistic, normal delays)
  • Pessimistic = 14 person-days (lots of bugs, env issues, rework)

PERT estimate = (4 + 4×7 + 14) / 6 = (4 + 28 + 14) / 6 = 46 / 6 ≈ 7.7 person-days.

💡 Interview tip: When asked "how do you estimate testing effort?", answer with 3-point (PERT) + a fallback to expert judgment. Mention that you always add a buffer (15-25%) for bug fixing, retesting, and environment issues — pure estimates are never enough.

What Makes Estimation Hard

  • Unclear requirements — you can't estimate what isn't defined.
  • Changing scope — every sprint adds stories, but the deadline doesn't move.
  • Unknown unknowns — integration bugs, environment outages, data issues.
  • Over-optimism — devs say "2 days for testing", reality is 5.
  • No historical data — first-of-a-kind features have no baseline.

21 Test Metrics & KPIs

Metrics turn subjective "we tested a lot" statements into objective numbers that teams and managers can act on. The key is to measure what matters, not what's easy to count.

Core Test Metrics — Formulas

Metric Formula What It Tells You Healthy Range (typical)
Defect Density Defects / Size (per KLOC or per function point) How buggy is a module / product? 0.5 - 5 per KLOC (varies)
Defect Leakage (Defects found in UAT or prod) / (Total defects) × 100 % of bugs that escaped testing. < 5% (target)
Test Case Effectiveness (Defects found by tests) / (Total test cases executed) × 100 Are your test cases actually finding bugs? Higher is better
Test Coverage (Test cases executed) / (Total test cases) × 100 % of planned testing actually run. ~100% at release
Requirements Coverage (Requirements covered by ≥1 test) / (Total requirements) × 100 Are all requirements actually tested? 100% (mandatory)
% Test Cases Passed (Passed test cases) / (Executed test cases) × 100 Overall product stability indicator. ≥ 95% for release
MTTD — Mean Time To Detect Total time from bug introduced to bug detected / Count of bugs How fast are we finding bugs? Lower is better
MTTF — Mean Time To Failure Total operational time / Number of failures Reliability metric for live systems. Higher is better
MTTR — Mean Time To Repair Total downtime / Number of failures How fast do we recover from a failure? Lower is better
Defect Removal Efficiency (DRE) (Bugs found before release) / (Bugs found before + after release) × 100 How effective was our testing at catching bugs? > 95% (excellent)

Example Calculation

A module has 1,000 lines of code. Testing found 8 bugs. UAT then found 2 more that escaped.

  • Defect Density = 8 / 1 KLOC = 8 bugs per KLOC (high — needs more review).
  • Defect Leakage = 2 / (8 + 2) × 100 = 20% (way above the 5% target — testing was insufficient).
  • DRE = 8 / 10 × 100 = 80% (target is > 95% — significant gap).

Good Metrics vs. Vanity Metrics

✅ Useful Metric (drives action) ❌ Vanity Metric (looks good, says nothing)
Defect leakage < 5% — tells you testing missed things. "We ran 5,000 test cases" — so what? Did they pass?
Requirements coverage = 100% — confirms full test scope. "We have 100 test cases" — quantity ≠ quality.
Defect removal efficiency > 95% — proves testing works. "We tested for 6 weeks" — duration alone means nothing.
% test cases passed per release — trend line over time. "We found 500 bugs" — finding bugs isn't the goal; shipping quality is.
⚠️ Common pitfall: Measuring only "test cases executed" or "bugs logged" can incentivize the wrong behavior — testers rushing through cases to hit a number, or logging trivial bugs to look productive. Pair quantity metrics with quality ones (leakage, DRE, customer-found defects).

22 Defect Triage & Bug Bashes

Not every bug is fixed immediately. Defect triage is the meeting where the team reviews new bugs and decides what to do with each one: fix now, fix later, reject, or defer to a later release.

What Happens in a Triage Meeting

Review new bugs
→
Validate (reproduce)
→
Set severity & priority
→
Decide action
→
Assign owner

Who Attends

  • Test Lead / QA Lead — chairs, ensures decisions are made.
  • Dev Lead / Senior Devs — estimate fix effort, identify duplicates.
  • Product Manager / Business Analyst — decides business priority.
  • Project Manager — updates release plan, tracks deferred items.

Triage Decisions

Decision When Outcome
Accept & Fix Now Critical / High priority, in-scope. Assigned to a dev, target this sprint.
Accept & Defer Valid but not urgent, or fixes touch risky areas late in cycle. Moved to the backlog for the next release.
Won't Fix (WontFix) Working as designed, cosmetic only, or out of scope. Documented and closed with reason.
Cannot Reproduce Not enough info, or environment-specific. Returned to tester for more details.
Duplicate Already reported as another bug. Linked and closed against the original.

Bug Bashes

A bug bash (or "bug hunt") is a focused, time-boxed event where the whole team (devs, testers, PMs, designers — anyone) tries to find as many bugs as possible in a specific area. They are short, social, and effective.

Aspect Best Practice
Duration 1 - 4 hours. Anything longer, attention drops.
Frequency Once per release, or before major milestones.
Scope A specific feature, flow, or the new build as a whole.
Participants Anyone in the org — fresh eyes find more bugs.
Recognition Small prizes for "most bugs", "weirdest bug", "best report".
Follow-up Triage all new bugs the next day; assign owners.
💡 Why bug bashes work: They (1) surface bugs the team missed because of familiarity, (2) build shared ownership of quality, and (3) give non-testers empathy for what testing actually involves.

23 Test Environment & Data Management

The test environment is the hardware, software, network, and data configuration on which you run your tests. A buggy environment produces unreliable results — and a surprising number of "bugs" reported by testers are actually environment issues.

Common Environment Types

Environment Purpose Who Owns It Test Data
Dev Developer local + shared dev server. Developers Synthetic / small
Test / QA Where testers run planned tests. QA Lead / Test Manager Masked production copy or curated
Staging / Pre-prod Production-like, used for UAT, performance, and final regression. DevOps / Release Manager Anonymized production data
UAT User Acceptance Testing — business / clients sign off here. Business / Product Owner Production-like
Production Live system. Only smoke tests and monitoring here. SRE / Ops Real data (PII protected)

Environment Readiness Checklist

  • ✅ Application build deployed and accessible.
  • ✅ Database at the right version, with the right data set.
  • ✅ All integrations / APIs reachable (or stubbed).
  • ✅ Test user accounts created with the right roles.
  • ✅ SSL, certificates, and domain / DNS configured.
  • ✅ Monitoring & logs accessible to the test team.
  • ✅ Access permissions set (testers can log in to all required systems).
  • ✅ Known-bug list shared so testers don't log them as new.

Test Data Management

Test data is often the hardest part of environment setup. It needs to be:

  • Realistic — represents production variety (names, addresses, edge cases).
  • Isolated — each tester / run has its own data, no overwrites.
  • Repeatable — you can re-run the same scenario with the same data.
  • Compliant — GDPR / HIPAA / PCI: no real PII (Personally Identifiable Information) in test environments.

Test Data Techniques

Technique Description When to Use
Synthetic Data Generation Use tools (e.g. Faker, Mockaroo) to generate fake but realistic data. When production data is too sensitive or unavailable.
Data Masking / Anonymization Replace real PII (names, emails, SSNs) with realistic but fake values. Always, when copying production data to test.
Data Subsetting Copy only a relevant slice of production data (e.g. one region's customers). When full prod data is too large.
Data Refresh Periodically reset test data to a known baseline. Before each test cycle or sprint.
On-the-Fly Data Creation Tests create their own data via API calls before running. Automation suites (self-contained, no shared state).
⚠️ Never use real customer data in lower environments. It's a compliance violation (GDPR fines can reach 4% of global revenue) and a security risk. Always mask before copying prod to test.

24 Risk-Based Testing

You can't test everything. Risk-based testing is the practice of prioritizing testing effort on the areas most likely to fail and most expensive if they do. It answers the question: "If I could only test 30% of this, which 30% matters most?"

The Risk Matrix

Each feature or area is scored on two axes:

  • Likelihood — how likely is it to fail? (low / medium / high)
  • Impact — how bad is it if it fails? (low / medium / high)
Low Impact Medium Impact High Impact
High Likelihood MEDIUM risk — test thoroughly. HIGH risk — test first, deeply. CRITICAL risk — fix before testing more elsewhere.
Medium Likelihood LOW risk — smoke test only. MEDIUM risk — test thoroughly. HIGH risk — prioritize.
Low Likelihood NEGLIGIBLE — skip or smoke only. LOW risk — quick check. MEDIUM risk — confirm with at least one test.

What Drives Risk

Factor Increases Risk If…
Complexity The code does many things, integrates with several systems, or uses new tech.
Criticality It handles money, PII, or safety. Downtime = lost revenue or legal issues.
Frequency of change The area is modified in every release.
History Many bugs were found here before.
Team familiarity New team or new domain — less institutional knowledge.
Time pressure Last-minute changes, rushed code, weekend deploys.

FMEA — Failure Mode and Effects Analysis

A structured risk-analysis technique. For each feature, list:

  1. Potential failure modes — what could go wrong?
  2. Effect of failure — what does the user experience?
  3. Severity — how bad? (1-10)
  4. Likelihood — how probable? (1-10)
  5. Detectability — how likely are we to catch it before release? (1-10, higher = less detectable)
  6. Risk Priority Number (RPN) = Severity × Likelihood × Detectability

Test the items with the highest RPN first.

Sample Risk Register

Feature Risk Likelihood Impact Risk Level Mitigation
Payment processing Wrong amount charged High High CRITICAL Exhaustive BVA + integration tests + manual smoke on every release.
Login Auth bypass / SQL injection Medium High HIGH Security testing, penetration test, rate-limit test.
User profile edit Data not saved Medium Medium MEDIUM Standard functional + regression.
Footer links Broken link Low Low LOW Smoke test only.
💡 When to use risk-based testing: (1) Tight deadlines — can't test everything. (2) Large, complex systems. (3) New releases with major changes. (4) When stakeholders ask "what didn't you test?" — the risk register is your answer.

25 Shift-Left & Continuous Testing

Shift-left testing means moving testing earlier in the development lifecycle — instead of testing only at the end (right), you test from the very beginning (left). The earlier a bug is found, the cheaper it is to fix.

The Cost of Late Bugs

Stage Found Relative Cost to Fix
Requirements 1× (cheapest)
Design 5×
Coding 10×
Integration testing 15×
System testing 50×
UAT 100×
Production 1000×+ (rewrites, hotfixes, customer trust, brand damage)

What Shift-Left Looks Like in Practice

  • Review requirements before they're final — catch ambiguity, missing acceptance criteria, untestable stories.
  • Write test cases alongside the story, not after the code is "done".
  • Pair with developers — test together during development.
  • Static analysis — run linters, security scans, and code-quality tools on every commit.
  • Unit tests by developers — testers define the cases; devs write the code.
  • Contract testing — verify API contracts between services before integration.

Continuous Testing (CT) in CI/CD

CT is the practice of running automated tests continuously — on every commit, on every merge, on every deploy — so quality feedback is immediate.

Test Pyramid (the Goal of CT)

The test pyramid shows the ideal mix of test types — lots of fast, cheap tests at the bottom, fewer slow, expensive tests at the top. 

        /\
       /  \      E2E / UI tests  (slow, few, high confidence)
      /────\

  /────────────\

Common Shift-Left / CT Tools

Stage Tools (examples) What They Do
Static analysis SonarQube, ESLint, Checkstyle, PMD Find code smells, security issues, style violations without running the code.
Unit testing JUnit, pytest, Jest, NUnit Test the smallest pieces of code in isolation.
API / Contract Postman, REST Assured, Pact Verify services talk to each other correctly.
UI / E2E Selenium, Cypress, Playwright Drive a real browser through user flows.
CI / CD Jenkins, GitHub Actions, GitLab CI, CircleCI Run all the above on every commit, deploy on green.
Observability Datadog, New Relic, Splunk, Grafana Watch production for issues, errors, and slow paths.

What Manual Testers Do in a CT World

Shift-left and automation do not eliminate manual testing — they change what testers do:

  • Earlier review — requirements, acceptance criteria, designs (before code exists).
  • Test design — write the test cases that automation will run, plus the exploratory scenarios.
  • Exploratory testing — the creative, judgment-based testing that scripts can't do.
  • Test automation — build and maintain the test scripts themselves.
  • Quality advocacy — push for quality across the team, not "QA at the end".
  • Test data & environment — keep the test platform healthy and reproducible.
💡 Mindset shift: In a CT / DevOps world, quality is everyone's job. The tester's role changes from "gate at the end" to "enable quality throughout." This is the future of the profession — embrace it.
