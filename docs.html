1 Introduction to Software Testing

What is Software Testing?

Software testing is the process of verifying and validating that a software application: (1) works as expected, (2) meets the requirements given by the client, and (3) is bug-free and ready for users. It's not just "clicking around" — it's a systematic, planned process.

Bug / DefectAny deviation between expected behavior and actual behavior.Expected "₹100" shown, but app shows "₹1000".

7 Principles of Software Testing

  1. Testing shows the presence of defects — testing can prove bugs exist, but can never prove the software is 100% bug-free.
  2. Exhaustive testing is impossible — you can't test everything (every input, every combination). Test smartly using techniques (BVA, EP).
  3. Early testing saves time & money — a bug found in requirements costs ~10x less than one found in production.
  4. Defects cluster together — a small number of modules contain most of the bugs (Pareto: ~80% of defects in ~20% of modules).
  5. Pesticide paradox — running the same tests again and again stops finding new bugs. Keep reviewing & adding new test cases.
  6. Testing is context dependent — a banking app needs different testing than a game or a website.
  7. Absence-of-errors fallacy — a bug-free system that doesn't meet user needs is still useless.
💡 Interview TipAlways remember: Verification = static review, Validation = dynamic execution. Interviewers love this simple distinction.
📝 Real-World Example — Your Fraud Background

In fraud investigation you looked for evidence of wrong transactions. Testing is identical: you look for evidence of wrong behavior in software. Both require: a clear expected standard, systematic checking, careful documentation, and proof (screenshots/logs). This is your superpower.

6 Test Design Techniques

These techniques help you choose which test cases to write so you find the most bugs with the fewest tests (remember: exhaustive testing is impossible).

1. Boundary Value Analysis (BVA)

Bugs happen most often at boundaries. Test the edges: just below, exactly at, and just above the boundary.

Example: Age field accepts 18 – 60

Valid boundaries: 17 (invalid), 18 (valid min), 59/60 (valid max), 61 (invalid).
BVA test values: 17, 18, 60, 61 — these 4 values cover the boundaries perfectly.

2. Equivalence Partitioning (EP)

Divide inputs into groups (partitions) that the system treats the same way. Test one value from each partition — no need to test every value.

Example: Marks field (0 – 100)

Invalid: negative (-5) Valid: 0 – 100 (e.g. 50) Invalid: above 100 (150)
One value per partition is enough: test -5, 50, 150.

3. Decision Table Testing

Use when there are multiple conditions that combine to give results. Build a table of condition combinations.

Login Box ConditionsCase 1Case 2Case 3Case 4
Username correct?✅✅❌❌
Password correct?✅❌✅❌
ResultLogin successError: wrong passwordError: wrong userError: both wrong

4. State Transition Testing

Use when the system changes states based on events. Track state changes and valid/invalid transitions.

Pending 🕐
pay
Paid ✅
deliver
Delivered 📦

Invalid: you should NOT be able to go from "Paid" directly back to "Pending".

5. Error Guessing

Using experience and intuition to guess where bugs might hide — testing common weak spots (empty inputs, special characters, spaces, huge inputs, rapid clicks).

⚠️ Interview FavoriteBe ready to explain BVA & EP with a live example. E.g. "For a field accepting 1–100, I test 0, 1, 100, 101 (BVA) and one value from each partition (EP)."

7 Test Cases & Test Scenarios

Definitions

  • Test Scenario: "What to test" — a one-line statement of a feature to test (e.g., "Verify user can log in").
  • Test Case: "How to test it" — step-by-step instructions including inputs, steps, and expected result.
  • Test Suite: A collection of test cases for a module/feature.

Anatomy of a Good Test Case

FieldDescriptionExample
Test Case IDUnique identifierTC_LOGIN_001
Title / SummaryWhat is being verifiedVerify successful login with valid credentials
PreconditionsSetup required before runningUser account exists, app is open
Test StepsNumbered actions1. Enter username. 2. Enter password. 3. Click Login.
Test DataInput values usedUsername: qa_user, Password: Pass@123
Expected ResultWhat should happenUser is redirected to the Dashboard
Actual ResultWhat actually happened (filled during execution)Error: "Invalid credentials" — BUG
StatusPass / Fail / Blocked / Not RunFail
PriorityOrder of execution (how urgent)High
SeverityImpact on the system (how bad)Critical

How to Write Good Test Cases (Checklist)

  • Use clear, simple, unambiguous language.
  • Each test case tests one thing.
  • Always include expected results (never leave blank).
  • Cover positive AND negative scenarios.
  • Cover boundary conditions.
  • Write steps anyone (even a new joiner) can follow.
  • Don't depend on other test cases.
  • Keep it maintainable & reusable.

Test Scenario vs Test Case — Example

Feature: Login Page

Scenario: Verify user can log in.
Test Cases derived from it:

  • TC1: Login with valid username + valid password → success
  • TC2: Login with valid username + invalid password → error message
  • TC3: Login with invalid username + valid password → error message
  • TC4: Leave both fields empty → validation error
  • TC5: Password with only 1 character (boundary) → error
  • TC6: "Remember me" checked → session persists after browser close
  • TC7: Click "Forgot password" → reset email sent

Severity ≠ Priority — Classic Example

High severity, low priority: Company LOGO is misspelled on the homepage. It's "trivial" visually but the client wants it fixed urgently because it's their brand. → Low severity (cosmetic) but High priority (business).

High priority, low severity: A rare button misalignment — but it's in the feature launching today, so it must be fixed. → Minor severity but High priority.

High severity, high priority: App crashes when making a payment. → Critical + P1.

RTM maps every requirement → test case → bug. It proves each requirement is tested. The key to 100% coverage.

11 Tools: Jira, SQL, Excel for Testers

Jira (Defect Tracking #1 tool)

Jira is used for tracking user stories, tasks, and bugs, and for managing Agile sprints.

  • Issue types: Story, Task, Bug, Epic, Sub-task.
  • Workflow: To Do → In Progress → In Review → Done (customizable).
  • Boards: Scrum board (sprints) or Kanban board (continuous).

Postman Workflow for Testers

  1. Create a Collection (group of requests).
  2. Add requests — method, URL, headers, body (JSON).
  3. Use Environment variables (base URL, token) so tests are reusable.
  4. Write Tests (e.g., pm.response.to.have.status(200)).
  5. Run collections, generate reports.
ℹ️ Practice OnlineUse free public APIs like reqres.in or jsonplaceholder.typicode.com to practice GET/POST without any setup.

13 Mobile Application Testing

Key Challenges in Mobile Testing

  • Device fragmentation — thousands of devices, screen sizes, OS versions.
  • Network variability — 2G/3G/4G/5G/WiFi, weak vs strong signals.
  • Battery & memory — apps must be efficient.
  • OS version differences — Android 11 vs 14, iOS 16 vs 17.
  • Interruptions — calls, SMS, notifications, low battery, screen rotation.

What to Test in a Mobile App

AreaTest Scenarios
Install / UninstallClean install, upgrade from older version, uninstall removes all data, reinstall.
UI / UXLayout on different screen sizes, rotation, dark mode, touch targets.
NetworkSlow network, no network, switch WiFi→4G mid-download, timeout behavior.
InterruptionIncoming call during payment, SMS during video, app goes to background.
OS behaviorPush notifications, permissions (camera/location), battery drain, force-stop & restart.
PerformanceCold start time, scrolling smoothness, memory usage, crash on low memory.
SecurityLocal data encryption, no sensitive data in logs, secure API calls.

14 Performance & Security Testing

Performance Testing Types

TypeGoalExample
Load TestingBehavior under expected normal load500 concurrent users using the app

Key Performance Metrics

  • Response Time — how fast the server responds.
  • Throughput — requests processed per second.
  • Latency — delay between request and response.
  • Error Rate — % of failed requests.
  • CPU / Memory usage — server resource consumption.
  • Concurrency — how many users at once.

Tool: JMeter (most common, free) — create test plans, thread groups (users), samplers (requests), and view reports.

Security Testing Basics — OWASP Top 10 (know the names)

  1. Broken Access Control — users can access data they shouldn't.
  2. Cryptographic Failures — weak/unsafe data encryption.
  3. Injection — SQL/XSS/Command injection.
  4. Insecure Design — flaws in the architecture.
  5. Security Misconfiguration — default passwords, open ports.
  6. Vulnerable & Outdated Components — old libraries.
  7. Identification & Auth Failures — weak login mechanisms.
  8. Software & Data Integrity Failures — untrusted updates.
  9. Security Logging & Monitoring Failures — no logs to detect attacks.
  10. Server-Side Request Forgery (SSRF) — server tricked into fetching malicious URLs.
⚠️ For Manual Tester InterviewsYou won't be expected to perform penetration testing — just know what security testing is, common attack types (SQL Injection, XSS), and that tools like Burp Suite / OWASP ZAP exist.

Test Automation Frameworks

  • Data-Driven: test data stored separately (Excel/CSV), same test runs with multiple data sets.
  • Keyword-Driven: keywords (like "login", "click") define test actions — non-coders can write tests.
  • Page Object Model (POM): each page of the app is a class; test code is clean and maintainable. Most asked in interviews.
  • Hybrid: combination of the above.

16 Portfolio Project — The Thing That Gets You Hired

No experience? No problem. Build a complete QA portfolio project on any public website (Amazon, Flipkart, Zomato, Swiggy, a banking app). Interviewers love to see real artifacts.

Your Portfolio Must Include

  1. Test Plan — scope, approach, entry/exit criteria, risks.
  2. 50+ Test Cases — organized by module (Login, Search, Cart, Payment, Orders).
  3. RTM — requirements → test cases mapping.
  4. 10+ Bug Reports — with screenshots, severity/priority, steps.
  5. Test Execution Summary — pass/fail %, defect analysis.
  6. SQL queries — sample queries to verify data.
