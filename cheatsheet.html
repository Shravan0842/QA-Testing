SDLC Models — one-liners:

  • Waterfall: Linear; each phase completes before next; testing at the end.
  • V-Model: Waterfall + testing mirrored at each level; testing planned early.

⚠️ Severity vs Priority — Cheat
Severity (how BAD) Priority (how URGENT)
Set by Tester PM / Product Owner
Levels Critical, Major, Minor, Trivial P1"“P4 (P1 = highest)
Example App crash = Critical Logo typo = often P1 (business)
Classic combinations

High Sev + High Pri App crashes on payment
High Sev + Low Pri Rare crash in an old rarely-used feature
Low Sev + High Pri Logo typo before a client demo
Low Sev + Low Pri Slight button alignment off

🗄️ SQL for Testers — Quick Commands
-- Read all columns
SELECT * FROM customers;

-- Filter rows
SELECT name, email FROM customers
WHERE status = 'active' AND city = 'Mumbai';

-- Join two tables
SELECT c.name, o.amount
FROM customers c
JOIN orders o ON c.id = o.customer_id;

-- Count & group
SELECT city, COUNT(*) FROM customers
GROUP BY city HAVING COUNT(*) > 5;

-- Verify a transaction
SELECT * FROM payments
WHERE order_id = 'ORD-1001';
Keyword Used for
SELECT / FROM Pick columns & table
WHERE Filter rows

GROUP BY Group for aggregates
HAVING Filter groups (after GROUP BY)
ORDER BY Sort (ASC/DESC)
LIKE Pattern match (LIKE '%gmail%')
IN / BETWEEN List / range filter
COUNT / SUM / AVG Aggregates
INSERT / UPDATE / DELETE Modify data

Test Design Techniques — Cheat
  • BVA (Boundary Value Analysis): test values at, just below, just above boundaries. Field 18"“60 → test 17, 18, 60, 61.
  • EP (Equivalence Partitioning): split inputs into groups; test 1 value per group. Valid 0"“100 → test 50; invalid → -5 and 150.
  • Decision Table: combinations of conditions & outcomes (best for business rules).
  • State Transition: valid/invalid state changes (e.g., Pending → Paid → Delivered).
  • Error Guessing: intuition-based — empty fields, special chars, rapid clicks, huge data.
  • Pairwise Testing: test all combinations of variables pairwise to reduce test count.
⚠️ Interview"For an age field accepting 1"“100: EP → test 0, 50, 101. BVA → test 0, 1, 100, 101." — know this cold.
Estimation, Entry/Exit & Metrics — Cheat

Estimation techniques:

  • Functional Point Analysis
  • Use-Case based
  • Test Point Analysis
  • Experience based

Entry criteria (START when):

  • Build deployed & testable
  • Environment + test data ready
  • Requirements & test cases reviewed

Exit criteria (STOP when):

  • All critical/major bugs closed
  • All planned tests executed
  • No P1 blockers, summary report signed off

Key metrics:

  • Test Case Pass % = (Passed ÷ Total Executed) × 100
  • Defect Density = Defects ÷ KLOC
  • Defect Removal Efficiency (DRE) = Defects found ÷ (Defects found + missed in production)

Top Interview Answers — One-Liners
Q: What is the difference between smoke and sanity testing?
Smoke checks that the whole build is testable (wide, critical features), while sanity checks one specific fix works (narrow).
Q: Regression vs Retesting?
Retesting re-runs the exact failed test case to verify a fix; regression tests the rest of the app to ensure nothing broke.
Q: What is the bug lifecycle?
New → Assigned → Open → Fixed → Retest → Closed, with possible Reopened, Deferred, or Rejected states.
Q: Severity vs priority?
Severity is how bad the bug is for the system (set by tester); priority is how urgent to fix (set by PM/business).
Q: What is a test plan?
A document covering scope, approach, resources, schedule, entry/exit criteria, and risks for testing a project.
Q: What is the STLC?
Software Testing Life Cycle: Requirement analysis, Test planning, Test case development, Environment setup, Execution, Closure.
Q: What is a traceability matrix?
A mapping of each requirement to its test cases and bugs, proving full coverage.
Q: When do you stop testing?
When exit criteria are met: all planned tests executed, critical bugs closed, risk acceptable, and report signed off.
Q: What is your role in a Scrum team?
Test stories in-sprint, write test cases from acceptance criteria, log bugs, do regression, demo quality at sprint review.
🔄 Shift-Left & DevOps Testing — Key Terms
Term One-line meaning
Shift-Left Move testing earlier in the SDLC — test from requirements onward, not just at the end.
Continuous Testing (CT) Run automated tests continuously (on every commit/merge/deploy) to get fast quality feedback.
CI (Continuous Integration) Merge code frequently (multiple times a day); auto-run build + unit + integration tests on every merge.
CD (Continuous Delivery / Deployment) Delivery: code is always deployable. Deployment: every green build goes live automatically.
Trunk-Based Development All devs commit to one shared branch (main/trunk); short-lived feature branches at most.
Blue-Green Deploy Two identical production environments; switch traffic from old (blue) to new (green) atomically; rollback = switch back.
Canary Deploy Release new version to a small % of users first; monitor; if OK, roll out to 100%.
Feature Flag Toggle a feature on/off in production without redeploying code. Enables testing in prod safely.
IaC (Infrastructure as Code) Define environments in version-controlled config files (Terraform, Ansible) — reproducible, testable.
Observability Understand a system's internal state from its external outputs: logs, metrics, traces (the "three pillars").
Chaos Engineering Intentionally inject failures (kill a server, slow the network) in production-like envs to test resilience.
📊 Test Metrics & KPIs — Formulas
Metric Formula Example
Defect Density Bugs / Size (per KLOC or per FP) 8 bugs in 4 KLOC = 2 per KLOC
Defect Leakage (Escaped bugs) / (Total bugs) × 100 2 escaped of 12 total = 16.7%
Test Coverage (Cases executed) / (Total cases) × 100 180 / 200 = 90%
Requirements Coverage (Reqs with ≥1 test) / (Total reqs) × 100 50 / 50 = 100%
% Test Cases Passed (Passed) / (Executed) × 100 170 / 180 = 94.4%
MTTD (Mean Time To Detect) Σ (time to detect each bug) / bug count (4 + 6 + 2) / 3 = 4 days
MTTR (Mean Time To Repair) Σ (time to fix each bug) / bug count (3 + 5 + 1) / 3 = 3 days
MTTF (Mean Time To Failure) Σ operational time / # failures 1000h / 5 = 200h between failures
Defect Removal Efficiency (DRE) (Bugs pre-release) / (Bugs pre + post) × 100 48 / 50 = 96%
Test Effectiveness (Bugs found by tests) / (Total cases run) × 100 20 bugs / 200 cases = 10%
Test Case Productivity Cases designed / Effort (person-hours) 100 cases / 25 hrs = 4 / hr
💡 Healthy targets: Defect leakage < 5%, DRE > 95%, requirements coverage = 100%, % passed ≥ 95% at release.
🧮 Test Estimation — Quick Math

3-Point (PERT)

Estimate = (O + 4M + P) / 6   where O = optimistic, M = most likely, P = pessimistic.

Example: O=4, M=7, P=14 → (4 + 28 + 14) / 6 = 7.7 person-days.

Wideband Delphi

  • Each expert estimates independently (no discussion).
  • Reveal all estimates. Discuss the gaps (outliers explain reasoning).
  • Re-estimate. Repeat 2-3 rounds until estimates converge (within 10-15%).
  • Final value = average of the last round.

Work Breakdown Structure (WBS)

Sum the estimates of all leaf-level tasks, then add a contingency buffer (15-25%) for risk.

Example: 10 tasks × 2 days each = 20 days. + 20% buffer = 24 days.

Use-Case Points (UCP) — quick version

UCP = (UUCW + UAW) × TCF × ECF

  • UUCW = Unadjusted Use Case Weight (count simple/avg/complex use cases × 5/10/15)
  • UAW = Unadjusted Actor Weight (count simple/avg/complex actors × 1/2/3)
  • TCF = Technical Complexity Factor (0.6 + 0.01 × ΣTi)
  • ECF = Environmental Complexity Factor (1.4 − 0.03 × ΣEi)

Then: Effort (person-hours) = UCP × Productivity factor (typical 20-30 hrs/UCP).

Estimation Tips

  • Always add a 15-25% buffer for bug fixes + retesting + env issues.
  • Round estimates to ½ or 1 day — finer precision is false confidence.
  • Re-estimate mid-sprint if assumptions change; don't pad silently.
  • Track actual vs estimated; learn your team's bias over time.

Device Coverage Strategy

  • Use a cloud device farm (BrowserStack, Sauce Labs, AWS Device Farm, Firebase Test Lab) for breadth.
  • Keep 3-5 physical devices in-house for the most popular models (latest iPhone, latest Samsung, a budget Android, a tablet, a foldable if relevant).
  • Test on the OS versions your users actually run — check analytics, not the newest only.
🌐 API Testing — Expanded Cheat

Authentication Types

Type How It Works Where to Use
None No credentials needed. Truly public APIs (weather, public data).
API Key Single secret in header or query string. X-API-Key: abc123 Internal services, simple server-to-server.
Basic Auth Username:password base64-encoded in header. Authorization: Basic dXNlcjpwYXNz Legacy, internal, low-security endpoints.
Bearer (Token) Opaque token issued by auth server. Authorization: Bearer eyJhbGciOi... Most modern REST APIs, JWTs.
OAuth 2.0 Delegated access with access + refresh tokens. Multiple grant types (auth code, client credentials, password). Third-party apps, "Login with Google/GitHub".
OpenID Connect Identity layer on top of OAuth 2.0. Returns ID token with user profile. SSO, "Sign in with X" experiences.
mTLS (Mutual TLS) Both client and server present certificates. B2B, financial, zero-trust networks.

Common Headers You'll See / Test

Header Purpose
Content-Type Format of the body. application/json, application/xml, multipart/form-data.
Authorization Carries the auth credential (Bearer, Basic, etc.).
Accept Tells the server which formats the client can handle.
User-Agent Identifies the client (browser, app version, OS).
X-Request-ID Correlation ID for tracing a request through logs.
Cache-Control Caching directives (no-cache, max-age=3600).
If-None-Match / If-Modified-Since Conditional GET — returns 304 if unchanged.

🔒 Security Testing — Basics

OWASP Top 10 (2021) — One-Liners

# Vulnerability What It Is
A01 Broken Access Control Users can act outside their permissions (e.g., view another user's data by changing the ID).
A02 Cryptographic Failures Weak / missing encryption of sensitive data in transit or at rest (HTTP instead of HTTPS, MD5 for passwords).
A03 Injection Untrusted input is run as code (SQL, NoSQL, OS command, LDAP).
A04 Insecure Design Architectural flaws — no rate limiting, missing threat modeling, business logic bypass.
A05 Security Misconfiguration Default passwords, open S3 buckets, verbose error messages, unnecessary features enabled.
A06 Vulnerable & Outdated Components Using libraries / frameworks with known CVEs and no update plan.
A07 Identification & Auth Failures Weak passwords, missing MFA, session fixation, credential stuffing not blocked.
A08 Software & Data Integrity Failures Unsigned updates, insecure CI/CD pipelines, auto-update without verification.
A09 Logging & Monitoring Failures Insufficient logging of security events; no alerting; no incident response plan.
A10 Server-Side Request Forgery (SSRF) Attacker makes the server fetch a remote resource (internal admin pages, cloud metadata).

Common Attacks — How to Test

Attack What You Try Where to Test
SQL Injection Enter ' OR '1'='1 in login / search; expect parameterized query to reject it. Any input field that hits a DB.
XSS (Cross-Site Scripting) Enter <script>alert(1)</script> in a name / comment field; expect it to be escaped, not executed. Any field whose content is later displayed.
CSRF Force a logged-in user's browser to submit a state-changing request from another site. State-changing endpoints (transfer, password change).
Broken Auth Brute force, session fixation, password reset poisoning, JWT signature stripping. Login, password reset, session handling.
Insecure Direct Object Reference (IDOR) Change an ID in the URL (/orders/123 → /orders/124); expect 403, not someone else's data. Any endpoint with user-supplied IDs.
Sensitive Data Exposure Inspect response body, network, source — passwords, tokens, PII should never appear in plain text.
Rate Limiting Send 1000 login attempts in 1 minute; expect 429 after a threshold.

Useful Security Testing Tools

  • OWASP ZAP — free, open-source web scanner. Great for beginners.
  • Burp Suite — industry-standard proxy + scanner for web apps.
  • Nessus / Qualys — vulnerability scanners for infrastructure.
  • Postman / REST Client — manual auth / header / injection testing on APIs.
  • SQLMap — automated SQL injection detection & exploitation.
  • Browser DevTools — always check Network, Application, Console for leakage.
⚠️ Always test on staging or with explicit written authorization. Scanning or attacking a production system without permission is illegal in most jurisdictions.
