Frequently asked interview questions with model answers. Click a question to reveal the answer, or use the accordion below.

1. Tell me about yourself (fresher QA). ▼
"I've recently completed a structured manual testing course and built a portfolio project on an e-commerce website. I've written a test plan, 50+ test cases using BVA and EP, logged bugs, and prepared a test summary report. I'm detail-oriented, good at documentation, and understand SDLC, STLC, Agile/Scrum, Jira, SQL, and Postman basics. I'm excited to join as a manual QA to ensure quality software."
2. What is SDLC? List the phases. ▼
SDLC (Software Development Life Cycle) is the process of building software. Phases: Requirements → Design → Development → Testing → Deployment → Maintenance. QA adds value in every phase.
3. What is STLC? ▼
STLC (Software Testing Life Cycle) is the testing process: 1. Requirement Analysis, 2. Test Planning, 3. Test Case Development, 4. Environment Setup, 5. Test Execution, 6. Test Closure.
4. Difference between Waterfall and Agile? ▼
Waterfall is linear — each phase completes before the next, testing happens at the end, changes are costly. Agile is iterative — work in short sprints, testing happens in every sprint with continuous feedback, and requirements can change quickly.
5. Difference between severity and priority? ▼
Severity measures how serious/impactful a bug is on the system (Critical, Major, Minor, Trivial) and is usually set by the tester. Priority measures how urgently it must be fixed (P1–P4) and is set by the PM/Product Owner. Example: a misspelled logo is low severity but can be high priority.
6. What is the bug/defect lifecycle? ▼
New → Assigned → Open → Fixed → Retest → Closed, with states like Reopened (fix didn't work), Deferred (fix later), and Rejected (not a bug / duplicate).
7. Difference between smoke, sanity, and regression testing? ▼
Smoke = quick check that the build is testable (wide, critical features). Sanity = quick check that one specific fix works (narrow). Regression = verify new changes didn't break existing functionality (wide).
8. How do you write a good test case? ▼
Clear ID, descriptive title, preconditions, test data, numbered steps, expected result, and later the actual result & status. Test one thing per case, cover positive + negative + boundary scenarios, and write it so anyone can follow. Example for login: enter valid username/password → expect dashboard.
9. What is boundary value analysis? Give an example. ▼
BVA tests values at, just below, and just above the boundaries of a field. For an age field accepting 18–60, I'd test 17, 18, 60, and 61 because bugs cluster at boundaries.
10. What is equivalence partitioning? ▼
EP divides inputs into partitions that the system treats the same way; test one value from each partition. For 0–100 marks: valid partition = 50, invalid = -5 and 150.
11. What is a test plan? What does it contain? ▼
A test plan is a document that defines the testing scope, approach, resources, schedule, entry/exit criteria, deliverables, and risks. It's the roadmap for testing.
12. What is RTM and why is it important? ▼
RTM (Requirement Traceability Matrix) maps each requirement to its test cases and bugs. It proves 100% requirement coverage and helps when requirements change — you can find which tests are affected.
13. What is entry and exit criteria? ▼
Entry criteria are conditions to START testing (build deployed, environment ready, test data available). Exit criteria are conditions to STOP (all tests executed, critical bugs closed, no blockers, report approved).
14. What is the difference between a bug, error, and failure? ▼
Error = mistake by a developer in code. Bug/Defect = deviation between expected and actual behavior found during testing. Failure = when a user experiences the defect at runtime.
15. What is positive and negative testing? ▼
Positive testing uses valid inputs and expects success (login with correct credentials). Negative testing uses invalid inputs and verifies proper error handling (wrong password shows an error, not a crash).
16. How would you test a login page? ▼
Test valid login, invalid username, invalid password, both empty, boundary on password length, special characters, "Remember me", forgot-password flow, session timeout, UI alignment on multiple screens, and verify error messages are correct and no crash occurs.
17. What do you do if a bug is not reproducible? ▼
Note the exact environment, time, steps; add screenshots/videos; ask the developer to test on their environment; check logs; add heap dump if possible; mark it as "sometimes/occasionally failed" and keep the bug open with all details.
18. The developer says "it's working on my machine". What do you do? ▼
Compare environments (OS, browser version, data, configs), reproduce with the exact build version, share screenshots/logs, and if it's truly environment-specific, document it clearly rather than arguing — evidence wins.
19. What is the difference between verification and validation? ▼
Verification is static — reviewing documents/design to confirm we're building it right (like a review). Validation is dynamic — executing the software to confirm we built the right product.
20. What is compatibility testing? ▼
Checking the application works across different browsers, OS, devices, screen sizes, and network conditions. After functional tests pass, verify look and behavior is consistent everywhere.
21. Why do we need SQL knowledge in testing? ▼
To verify data stored correctly in the database (e.g., a payment is recorded), to prepare test data, to validate reports, and to check the backend of features — the UI may show success but the DB may reveal issues.
22. Name the HTTP status codes you know. ▼
2xx success (200 OK, 201 Created), 3xx redirection (301/302), 4xx client errors (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found), 5xx server errors (500 Internal Server Error, 503 Service Unavailable).
23. What is API testing? ▼
Testing backend APIs directly (without UI) to verify request/response logic, status codes, data validation, authentication, and business rules. It's faster and tests core logic before UI.
24. Difference between int, smoke, and regression in one sentence each? ▼
Integration = modules working together. Smoke = quick build-stability check. Regression = nothing broke after changes.
25. What is a retest? ▼
Retesting is re-running the exact test case that failed, after a developer has fixed the bug, to confirm the fix works.
26. What is exploratory testing? ▼
Unscripted, creative testing where the tester explores the application, learns it as they go, and uses intuition and experience to find bugs that scripted tests might miss.
27. What is the role of a tester in an Agile team? ▼
Participate in sprint planning and backlog refinement, write test cases from acceptance criteria early, test features as they're developed, log and track bugs, do regression each sprint, and give fast feedback to help deliver quality increments.
28. What is performance testing? What types exist? ▼
Performance testing checks speed, responsiveness, and stability. Types: Load (expected load), Stress (beyond limits), Endurance (long duration), Spike (sudden load), Volume (large data). Tool: JMeter.
29. What is the difference between load and stress testing? ▼
Load testing verifies the system works fine under expected/peak load. Stress testing pushes beyond limits to find the breaking point and how the system fails (and recovers).
30. What is UAT? ▼
User Acceptance Testing — performed by real business users/clients in an environment close to production to confirm the software meets their business needs before release.
31. What do you know about mobile testing challenges? ▼
Device fragmentation (many devices/OS/screens), network variability (2G–5G, WiFi), interruptions (calls, SMS, notifications), battery/memory constraints, and OS version differences. Test install/uninstall, permissions, rotation, and performance too.
32. What is the difference between emulator and real device? ▼
An emulator/simulator is a software copy on the computer — fast and free for early functional testing. A real device behaves realistically (sensors, network, battery) and is needed for final verification.
33. What is security testing? What do you know? ▼
Security testing checks the app is protected from attacks and data leaks — e.g., SQL injection, XSS, broken authentication, insecure data storage. I'm familiar with OWASP Top 10 and basic testing of authorization, encryption, and session handling.
34. What is automation testing? Do you know Selenium? ▼
Automation uses tools to run tests repeatedly and fast (Selenium, Cypress, Playwright). I understand the concept, when to automate (repeated regression, large data) vs not (usability, exploratory), and frameworks like Data-Driven and Page Object Model. I'm learning the basics to grow into automation.
35. What is the "Page Object Model"? ▼
POM is an automation design pattern where each page of the app is represented by a class. Test code says "loginPage.login()" instead of messy selectors — making tests cleaner, reusable, and easier to maintain.
36. What is the difference between a defect and a failure? ▼
A defect is the coding problem (found during testing). A failure is when an end-user observes that defect in production.
37. What is "defect density"? ▼
The number of defects per unit of software size (e.g., per 1000 lines of code). It helps measure which modules are most buggy and quality of code.
38. How do you prioritize which test cases to run first? ▼
Run: (1) smoke/high-priority critical paths, (2) test cases matching recent changes, (3) high-risk modules (payments, login), then (4) lower-risk and cosmetic areas. Time-box testing based on risk.
39. What is a traceability matrix used for during requirement changes? ▼
When a requirement changes, the RTM helps identify exactly which test cases are affected and must be updated and re-run — ensuring nothing is missed.
40. What is the difference between "defect rejection" and "defect deferred"? ▼
Rejected = the defect is not valid (not a bug, duplicate, or by design). Deferred = the defect is valid but will be fixed in a future release, not this one.
41. What is a "smoke test" and why is it the first test? ▼
A smoke test quickly checks the critical functionality (app opens, login works, main pages load). It's run first on each build to decide whether the build is stable enough to accept for deeper testing.
42. What is your understanding of "quality assurance vs quality control"? ▼
QA is proactive — improving the process to prevent defects. QC is reactive — verifying the product to detect defects. Testing is part of QC.
43. What is an epic, story, and task? ▼
Epic = large feature that's broken down. Story = a user-valued feature in user-story format. Task = a piece of work that contributes to finishing a story (e.g., "write test cases for login").
44. How do you handle a massive release with tight deadlines? ▼
Prioritize by risk — test critical/high-risk modules first, use smoke and sanity checks, apply BVA/EP for efficient coverage, communicate risks early to the PM, and clearly report what is untested so the team makes an informed release decision.
45. What is the "test summary report"? ▼
The closing document of testing that summarizes what was tested, pass/fail percentages, defects found and closed, coverage achieved, risks, and the release recommendation (go / no-go).
46. What are the 7 principles of testing? ▼
1. Testing shows presence of defects. 2. Exhaustive testing is impossible. 3. Early testing saves money. 4. Defects cluster. 5. Pesticide paradox. 6. Testing is context-dependent. 7. Absence-of-errors fallacy.
47. What is the difference between functional and non-functional testing? ▼
Functional testing checks WHAT the system does (features work per requirements). Non-functional testing checks HOW it performs — performance, security, usability, compatibility, accessibility.
48. When would you reject a build? ▼
When smoke/critical tests fail — for example, the app won't launch or login consistently fails. Rejecting early saves the team from testing a broken build. Always document why it was rejected.
49. What is "testing is context-dependent"? ▼
Testing approach depends on the application — a banking app needs heavy security/transaction testing, a game needs performance/UX, a website needs compatibility. There's no single correct approach for everything.
50. Why should we hire you as a QA tester? ▼
"I'm highly detail-oriented and analytical — I've spent 2 years in fraud investigation, where I examined transactions, followed evidence, and documented findings precisely. That's exactly what a good tester does: investigate behavior, find discrepancies, and document evidence. Plus I've completed structured QA training with test cases, bug reports, and a portfolio project, and I understand Jira, SQL, Postman, and Agile. I'll bring both discipline and a genuine passion for finding defects."
